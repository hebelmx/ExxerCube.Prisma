## 2. Usability Observations

| Aspect | Observation | Status | Evidence |
|--------|-------------|--------|----------|
| Navigation — unauthenticated state | All primary navigation items are visible to unauthenticated users, including auth-gated sections (Manual Review, Export Management, Audit Trail). Auth-protected items render with a warning/triangle badge (visible in `screen-home.png`). This communicates "broken" rather than "requires login". A cleaner pattern would be to hide items entirely or show a lock icon with a tooltip. | NEEDS HUMAN REVIEW | `screen-home.png`; `NavMenu.razor` lines 39–45 (AllowDevNavigation guard) |
| Navigation — route mismatch in evidence harness | The evidence harness probed `/review`, `/export`, `/audit`, `/sla` (returning 4,254 B identical blank pages). The actual product routes are `/manual-review`, `/export-management`, `/audit/viewer`, `/sla-dashboard`. The harness evidence for those 4 routes is therefore not informative about the real pages. Real routes confirmed working from direct live probes. | NEEDS HUMAN REVIEW | `screenshot-run.log` lines 5–8; live probes confirming real routes return 200/302 |
| Navigation — Development mode exposure | In Development mode the NavMenu exposes a "Development Quick Access" section listing all pages including auth-gated ones, plus an alert: "Every page is temporarily accessible while debugging". This is valuable for dev but creates risk if Development mode is inadvertently left on in production or staging. No config-guard prevents it. | NEEDS HUMAN REVIEW | `NavMenu.razor` line 143: `AllowDevNavigation => HostEnvironment.IsDevelopment() || Debugger.IsAttached` |
| Error messaging — health endpoint | `/health` returns the single word `Unhealthy` with no breakdown, no JSON, no component detail. An operator monitoring the system cannot determine which subsystem failed without accessing internal logs. PRD NFR11 requires structured logging with correlation IDs; the health response does not meet even the basic structured-output bar. | FAIL | Live probe: `curl http://localhost:5172/health` body = `Unhealthy` |
| Error messaging — export failure | When DatosCargaOficio generation starts but does not complete (EX-01), there is no user-visible error message or UI feedback. The export screen would show an in-progress state with no resolution or timeout alert. PRD FR14 (manual review) and general UI guidance (CR3 — loading states, error display) require consistent error feedback. | NEEDS HUMAN REVIEW | `e2e-rerun.log` line 426: generation starts; no completion line; RERUN-SUMMARY §failing assertion |
| Error messaging — low-confidence classification | A classification confidence of 10 (very low) produces a `WRN` log and two review cases, but the user-facing processing dashboard shows no indicator that this document is at critical low confidence. The pipeline continues to produce SIRO XML output for an unverified record. A compliance officer would not know to intervene. | NEEDS HUMAN REVIEW | `e2e-rerun.log` line 395: `WRN` low confidence; line 421: export proceeds |
| Login form — professional presentation | The login page (`screen-login.png`) renders with a default ASP.NET Identity scaffold panel on the right side pointing users to external ASP.NET documentation. This degrades the product's professional appearance for a regulated financial context. | FAIL | `screen-login.png` right panel; `Login.razor` (ASP.NET scaffolded component) |
| Workflow clarity — Manual Review to Export path | PRD Story 1.6 AC5 says review decisions update the unified metadata record before export. EX-06 shows the pipeline routes low-confidence documents directly to Stage 5 export without requiring review resolution. This creates ambiguity for a compliance officer: did the exported SIRO XML incorporate a reviewed record or an unreviewed one? | NEEDS HUMAN REVIEW | `e2e-rerun.log` lines 395–421; `ManualReviewDashboard.razor` (FR14 flow) |
| User effort — boot without database | The app boots and serves the home page when the database is unavailable (`/health` = 503, boot log shows seed failure). From a user-effort perspective this is reasonable (gradual degradation). However, there is no prominent UI banner on the home page informing the user that the system is running in degraded mode. PRD UI guidelines require loading states and error display. | NEEDS HUMAN REVIEW | `http-probes.txt`; `screen-home.png` (no degraded-mode banner visible) |
| Accessibility — WCAG 2.1 AA | PRD UI Consistency section requires WCAG 2.1 AA. Automated assessment is not possible without interactive session and accessibility tooling. Warning triangle badges on nav items and colour-only differentiation of severity in the dashboard metrics (red/green/orange MudBlazor chips with no alternative text cues) are potential concerns. | NEEDS HUMAN REVIEW | `screen-home.png`; `screen-dashboard.png`; PRD "Accessibility: Follow WCAG 2.1 AA standards" |
| Responsive design | PRD requires responsive design on desktop and tablet. Screenshots were captured at 1280x720 (desktop). No tablet or mobile viewport evidence available. | NEEDS HUMAN REVIEW | `screen-home.png`; PRD "Responsive Design: All new screens must be responsive and work on desktop and tablet devices" |
| Discoverability — System Flow dashboard | The sidebar includes "System Flow" which opens a rich multi-step flow dashboard (`SystemFlowDashboard.razor`). Discoverability of this screen vs. the operational screens (Manual Review, SLA) is unclear. | NEEDS HUMAN REVIEW | `screen-home.png` nav shows "System Flow"; `SystemFlowDashboard.razor` exists |

## 3. Method

**Sources consulted (in order):**
1. PRD (`docs/product/requirements/prd.md`) — read in full to establish expected behaviours for all 5 new screens, auth requirements, NFRs, and UI guidelines.
2. Evidence bundle MANIFEST — read to understand what was captured and under what conditions.
3. Pipeline E2E log (`e2e/e2e-rerun.log`) — read in full (483 lines); traced each pipeline stage entry and exit.
4. RERUN-SUMMARY — read for structured interpretation of the E2E failure point.
5. Screenshots — viewed all 8: home, login, dashboard, and the 5 auth-protected screens (blank/redirect).
6. Live HTTP probes — curled: `/`, `/health`, `/health/live`, `/health/ready`, `/dashboard`, `/Account/Login`, `/review`, `/export`, `/audit`, `/sla` (wrong harness paths), then `/manual-review`, `/export-management`, `/sla-dashboard`, `/audit/viewer` (correct paths) to verify auth behaviour.
7. Source files — read `NavMenu.razor`, `NavigationRegistry.cs` (partial grep), `ManualReviewDashboard.razor` (partial), `SlaDashboard.razor` (partial), `ExportManagement.razor` (partial), `AuditTrailViewer.razor` (route only) to correlate screenshot observations with code.

**What was not tested:** Authenticated user flows (no test credentials), mobile viewports, accessibility tooling, digital signing (FR16), SLA escalation notifications, identity resolution UI, bulk export, admin routes.

**Evidence rules applied:** Every finding cites a specific log line, HTTP response, or screenshot filename. Observations without direct evidence are classified NEEDS HUMAN REVIEW.
