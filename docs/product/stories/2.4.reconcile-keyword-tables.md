# Story 2.4: Reconcile Classifier Keyword Tables Against Generator Prose

**Status:** Draft
**Epic:** 2 - Confidence Pipeline Hardening & Re-architecture
**Stage:** Stage 4 - Classification
**Created:** 2026-06-25

---

## Story

**As a** compliance engineer,
**I want** the classifier keyword tables to include the actual phrasing emitted by the document generator for each requirement type,
**so that** classification is reliable across all synthetic test documents and reflects the real legal prose used in Mexican regulatory directives.

---

## Acceptance Criteria

1. The `OperacionesIlicitas` / PLD keyword list in `FileClassifierService.cs:159-172` includes normalized upper-case variants of "recursos de procedencia ilícita" and "operaciones inusuales" — the phrases actually emitted by the generator for that type.
2. A unit test `ClassifyAsync_PldDocumentWithGeneratorProse_ClassifiesOperacionesIlicitas` asserts that a `combinedText` containing only `"RECURSOS DE PROCEDENCIA ILICITA"` (or `"OPERACIONES INUSUALES"`) classifies as `OperacionesIlicitas` with `Confidence >= 70`.
3. A cross-reference table (in a code comment above each keyword list in `FileClassifierService`) documents the generator source (`legal_catalog.py` section and line range) for each Level-1 category keyword set.
4. For every Level-1 category, at least one generator prose phrase is represented in the keyword list; any category with zero coverage is flagged with a `// TODO(2.4): no generator phrases covered` comment for follow-up.
5. No existing passing classifier test regresses.
6. `dotnet build` 0/0.

---

## Integration Verification

- **IV1:** Keyword additions are additive; they must not remove or narrow any existing keyword that causes currently-passing tests to fail.
- **IV2:** All added keywords must be normalized to upper-case invariant to match the `.ToUpperInvariant()` call in `FileClassifierService.cs:44`.
- **IV3:** The generator source (`Prisma/Code/Src/Python/prisma-ai-extractors/` or `Prisma/Code/Src/Python/prisma-ocr-pipeline/`) and `legal_catalog.py` file must be read-only during this story — no generator changes.

## Dev Notes

### Inspection Evidence

Source: `docs/planning-artifacts/remediation/CONFIDENCE-PIPELINE-DEEP-INSPECTION-2026-06-25.md` §5 T2.2

**The specific miss identified (§5 T2.2):**
> "PLD relies on `LAVADO`/`OPERACIONES ILICITAS` but the generator emits *'recursos de procedencia ilícita'* / *'operaciones inusuales'* — a genuine miss for that type (`FileClassifierService.cs:159-172` vs `legal_catalog.py`). Reconcile the keyword tables against the generator's actual prose per requirement type."

**The generator sources cited (§2.3):**
```
Generator core/legal_catalog.py:190-194, 222-226 — emits for aseguramiento:
  "se solicita el aseguramiento precautorio de las cuentas bancarias"
  "Proceder al aseguramiento inmediato"
  "Notificar el monto total asegurado"
```
The analogous PLD section in `legal_catalog.py` (locate by searching for "procedencia ilícita", "operaciones inusuales", or the PLD/LAVADO category) is the primary source for this story.

**Normalization contract (§2.1):**
`FileClassifierService.cs:44` calls `.ToUpperInvariant()` on `combinedText` before matching. All added keywords must already be upper-case or the comparison will silently fail.

**Important caveat — do not remove keywords:**
The inspection recommends reconciling keyword sets, not purging them. A keyword absent from the generator may still appear in real SIARA documents. Mark phantom entries with a comment rather than deleting them.

### Change-Impact Tests (§4.4)

`ReconciliationPipelineServiceTests.cs:199,204` — pins reason strings that may include category names. Confirm that adding PLD keywords does not accidentally reroute any test document that previously classified correctly under a different category.
