# Story 2.5: Classifier Confidence as a Real, Documented Score

**Status:** Draft
**Epic:** 2 - Confidence Pipeline Hardening & Re-architecture
**Stage:** Stage 4 - Classification
**Created:** 2026-06-25

---

## Story

**As a** compliance engineer reviewing classification outputs,
**I want** the classifier confidence value to carry a documented, semantically meaningful score,
**so that** I can interpret a confidence of 80 as "strong keyword coverage" and a confidence of 45 as "weak or partial match" rather than a side-effect of an undocumented bucket-spread heuristic.

---

## Acceptance Criteria

1. `FileClassifierService.CalculateConfidence` (`cs:205-236`) is refactored so that each code path has an XML doc comment (or an inline comment block) stating: what input pattern triggers it, what the output range is, and what the confidence band means in terms of keyword match strength and coverage.
2. The no-match path (all scores at floor) returns `0` as specified in Story 2.2 (not `10`); this story documents that as the explicit zero-coverage band.
3. The function is covered by a dedicated parameterized unit test `CalculateConfidence_VariousInputPatterns_ReturnsExpectedBand` with at least 4 cases: (a) no keywords, (b) one strong hit, (c) multiple weak hits only, (d) mixed strong + weak.
4. The existing test assertions in `ReconciliationOrchestratorExportGateTests.cs` (confidence values 50, 95, 30, 90) remain valid and green after the refactor.
5. No change to the `IFileClassifier` public interface signature.
6. `dotnet build` 0/0.

---

## Integration Verification

- **IV1:** The refactored `CalculateConfidence` must remain a pure function (no I/O, no side effects) so that existing unit tests can call it deterministically.
- **IV2:** If the heuristic bands change numerically (e.g. a weak-hit now returns 55 instead of 70), the threshold-sensitive tests in `ReconciliationOrchestratorExportGateTests.cs` must be updated in the same PR and must not silently pass by coincidence.
- **IV3:** This story does not introduce the `Confidence` value object (that is Story 2.6); the output remains `int 0–100` for now. The documentation must note the planned migration.

## Dev Notes

### Inspection Evidence

Source: `docs/planning-artifacts/remediation/CONFIDENCE-PIPELINE-DEEP-INSPECTION-2026-06-25.md` §2.4, §5 T2.3

**The heuristic as it stands (§2.4):**
```
CalculateConfidence (FileClassifierService.cs:205-236):
  maxScore=10, averageScore=10, scoreDifference = 10 − (empty set→0) = 10
  10 < 40 → Math.Min(70, averageScore) = 10
```
Score 90 (strong hit) → `scoreDifference 80 ≥ 60` → confidence ~90%. The spread is the gap between the top category and the rest; large spread = dominant winner = high confidence. This is a reasonable proxy for classification certainty but is nowhere documented.

**The systemic problem (§3.4 item 5):**
> "Two classification confidences on two scales (`ClassificationResult.cs:28` int vs `ExpedienteClassificationResult.cs:33` double); the gate uses the int one."

This story documents the int-based heuristic; Story 2.6 will migrate both to the `Confidence` value object.

**The hardening prescription (§5 T2.3):**
> "Make the classifier confidence a real score, not a spread-of-keyword-buckets heuristic (`FileClassifierService.cs:205-236`) — at minimum document the band semantics; ideally derive from match strength/coverage."

This story targets "at minimum document the band semantics." The deeper scoring redesign (if warranted) is deferred to a follow-up spike.

### Change-Impact Tests (§4.4)

`ReconciliationOrchestratorExportGateTests.cs` lines 149/201/251/314/361/403 — use confidence values 50/95/30/90 in assertions around the 70 threshold. These must remain valid. If the refactor shifts any band boundary, these tests must be updated in the same PR.

`ProcessingOrchestratorTests.cs:541` — uses confidence 45 to trigger a review flag (below 70). Must remain green.
