# Story 2.3: Classifier Consults Structured Signals (TieneAseguramiento and Expediente Flags)

**Status:** Draft
**Epic:** 2 - Confidence Pipeline Hardening & Re-architecture
**Stage:** Stage 4 - Classification
**Created:** 2026-06-25

---

## Story

**As a** pipeline engineer,
**I want** Stage 4 classification to consult the structured boolean signals already present in the fused `Expediente` (e.g. `TieneAseguramiento`),
**so that** the classifier has a richer, more reliable signal than keyword substring matching alone and can produce stable high-confidence results even for documents with sparse OCR text.

---

## Acceptance Criteria

1. When `Expediente.TieneAseguramiento == true` is present in the fused result at Stage 4, the classification result is `Aseguramiento` with `Confidence >= 80`, regardless of whether the body text contains the keyword substring.
2. The implementation follows one of these two architecturally-acceptable approaches (the implementing agent must choose and record the rationale):
   - **Option A:** Route Stage-4 classification through `ExpedienteClasifierService` (which already returns 0.90 for `TieneAseguramiento` at `cs:379`) and wire it in both orchestrator call sites alongside or instead of `FileClassifierService`.
   - **Option B:** Fold the boolean-flag logic from `ExpedienteClasifierService.cs:365-409` into `FileClassifierService`, so one service handles both substring and structured-signal paths.
3. At least one unit test covers the structured-signal path: `ClassifyAsync_WithTieneAseguramientoTrue_ReturnsAseguramientoHighConfidence`.
4. At least one integration test verifies that a `FusedExpediente` with `TieneAseguramiento=true` and sparse OCR text still produces `Aseguramiento >= 80` end-to-end through the orchestrator call site.
5. Existing substring-matching behavior for documents without structured signals is not degraded — all pre-existing classifier tests pass.
6. `dotnet build` 0/0.

---

## Integration Verification

- **IV1:** The chosen approach must not create two competing `IFileClassifier` registrations in the DI container at `Reconciliator Program.cs:151` and `Athena Program.cs:163` — only one registration per composition root.
- **IV2:** `ExpedienteClasifierService.cs` lives in `Infrastructure.Classification`; if Option A is chosen, the DI wiring must reference the correct type from that namespace without creating a circular dependency.
- **IV3:** The `Result<T>` pattern must be preserved end-to-end; the chosen approach must not throw on a null `Expediente` or null boolean flag.

## Dev Notes

### Inspection Evidence

Source: `docs/planning-artifacts/remediation/CONFIDENCE-PIPELINE-DEEP-INSPECTION-2026-06-25.md` §3.1, §5 T2.1

**What `ExpedienteClasifierService` already does (§3.1):**
```
| 4′ Classification (Expediente-level, not gated) | ExpedienteClasifierService.cs:365-409 | double | 0–1 (hardcoded 0.80–0.95) |
```
This service already returns `0.90` for `TieneAseguramiento` (`cs:379`) but is **not** the wired classifier — `FileClassifierService` is wired at both composition roots (`Reconciliator Program.cs:151`, `Athena Program.cs:163`).

**The structured signal in the corpus (§2.3):**
The XML companion for `IMSS-2023-171230` carries `<TieneAseguramiento>true</TieneAseguramiento>`, and `FusionExpedienteService` populates `Expediente.TieneAseguramiento` from it. This flag is already in the fused result that the orchestrator holds at Stage 4 — it just is not consulted by `FileClassifierService`.

**The hardening prescription (§5 T2.1):**
> "Consult structured signals, not just substrings. `Expediente.TieneAseguramiento == true` should drive the Aseguramiento decision directly; today it's ignored (`ExpedienteClasifierService.cs:379` already returns 0.90 for it but is **not** the wired classifier). Decide: route Stage 4 through `ExpedienteClasifierService`/`ClassificationDictionary` (richer, fuzzy, handles the boolean) or fold those signals into `FileClassifierService`."

### Change-Impact Tests (§4.4)

No threshold values change in this story. The main risk is the DI wiring change (IV1). `ReconciliationOrchestratorExportGateTests.cs` and `ProcessingOrchestratorTests.cs:541` should be reviewed to confirm they do not rely on `FileClassifierService` being the only registered `IFileClassifier`.
