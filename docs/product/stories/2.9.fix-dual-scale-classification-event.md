# Story 2.9: Fix Dual-Scale Confidence on ClassificationCompletedEvent

**Status:** Draft
**Epic:** 2 - Confidence Pipeline Hardening & Re-architecture
**Stage:** Stage 4 - Classification (Events)
**Created:** 2026-06-25

---

## Story

**As a** developer consuming domain events from the Prisma pipeline,
**I want** `ClassificationCompletedEvent` to carry exactly one confidence value on one consistent scale,
**so that** I do not have to reason about whether `.Confidence` (int 0–100) or `.ConfidenceScore` (double 0–1) is authoritative, or risk producing silent bugs by reading the wrong field.

---

## Acceptance Criteria

1. `ClassificationCompletedEvent` (`Domain/Events/ClassificationCompletedEvent.cs`) carries exactly one confidence field: `Confidence` of type `Confidence` (the value object introduced in Story 2.6), on the 0–1 scale.
2. The redundant field is removed (either the `int Confidence` at `:24-26` or the `double ConfidenceScore` at `:51-53`, whichever is the lesser-referenced one; the other is renamed/replaced with the `Confidence` value object).
3. All event publishers that set `ClassificationCompletedEvent.Confidence` or `.ConfidenceScore` are updated to set the single `Confidence Confidence` field using `Confidence.FromPercentage(...)` or `Confidence.FromValue(...)` as appropriate.
4. All event subscribers and handlers that read either field are updated to read `event.Confidence.Value`.
5. A unit test `ClassificationCompletedEvent_HasSingleConfidenceField_OnValueObjectScale` asserts: the event carries the new field type, the old field names do not exist (compile-time check), and the value round-trips through `FromPercentage(90).Value == 0.90`.
6. All tests that reference `ClassificationCompletedEvent.Confidence` (int) or `.ConfidenceScore` (double) are updated to the new field; no test silently passes by reading a now-deleted property via a dynamic or reflection path.
7. `dotnet build` 0/0.

## Dev Notes

### Inspection Evidence

Source: `docs/planning-artifacts/remediation/CONFIDENCE-PIPELINE-DEEP-INSPECTION-2026-06-25.md` §3.4 item 6, §5 T3.4

**The dual-field defect (§3.4 item 6):**
> "One event carries **both** scales: `ClassificationCompletedEvent.Confidence` int (0-100) **and** `.ConfidenceScore` double (0-1) — `Domain/Events/ClassificationCompletedEvent.cs:24-26, 51-53`."

Specifically:
- Line 24-26: `int Confidence` (the 0–100 keyword-bucket score).
- Line 51-53: `double ConfidenceScore` (the 0–1 scale equivalent).

This duplication means any consumer must choose which one to trust, and a buggy consumer that reads the wrong field silently receives a 90x-off value (e.g. reading `int 90` as if it were `double 0.90` produces no error but a meaningless comparison).

**The fix prescribed (§5 T3.4):**
> "Fix the dual-scale event `ClassificationCompletedEvent` (§3.4.6) to carry a single `Confidence`."

**Dependency on Story 2.6:**
Story 2.6 introduces the `Confidence` value object with `FromPercentage` and `FromValue` factory methods. Story 2.9 cannot be implemented until that type exists. The `// TODO(2.9)` comment added to `ClassificationCompletedEvent.cs` by Story 2.6 serves as the handoff marker.

**Serialization note:**
If `ClassificationCompletedEvent` is persisted by `EventPersistenceWorker` (which subscribes to `GetAllEventsStream()`), removing a field constitutes a breaking serialization change. The implementing agent must check whether events are stored in a database or message bus and — if so — determine whether a migration or event-versioning strategy is needed. If no persistence exists (in-memory only), deletion is safe.

### Change-Impact Tests (§4.4)

`ReconciliationPipelineServiceTests.cs:199,204` — pins reason strings from the reconciliation pipeline; check if these capture or assert on the event's confidence field.

Any test in `Tests.Application` or `Tests.Infrastructure.Classification` that constructs or asserts on `ClassificationCompletedEvent` must be found via grep and updated.
