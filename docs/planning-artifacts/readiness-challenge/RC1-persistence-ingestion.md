## 2. Key-Management Assessment (config-secret vs KMS — what a bank/auditor needs)

**What is built:** AES-256-CBC encryption-at-rest for the legal-baseline tolerance decimals, with a 32-byte key supplied through `IConfiguration` (`ConfigurationCryptoKeyProvider.cs`). Each write generates a fresh random 16-byte IV prepended to the ciphertext (`AesEncryptedDecimalConverter.cs:42,47`) — IV reuse is correctly avoided.

**What a bank/auditor demands and is NOT present:**
1. **Key custody.** The key is a plaintext Base64 string in configuration. There is no KMS/HSM/Azure Key Vault/AWS KMS integration. For a load-bearing regulated processor, the key must live in a managed key store with access logging; a config secret (env var or appsettings) is below the bar. The code's own doc-comment admits this ("use Azure Key Vault — not appsettings") but nothing enforces or implements it.
2. **Rotation.** The key is read once at construction and cached for the process lifetime (`:60`); there is no rotation mechanism, no key-versioning, and ciphertext carries no key identifier — so a rotated key cannot decrypt historical rows (the IV is stored but the key-id is not). Rotation would require re-encrypting the table.
3. **Envelope encryption / DEK-KEK split.** Single-key design; no data-encryption-key wrapped by a key-encryption-key. Auditors expect envelope encryption for at-rest data.
4. **TDE / DB-level at-rest.** Column-level AES only covers the tolerance decimals; `SqlLegalBaselineStore.cs:20` explicitly states DB-level TDE is "an additional OPS provisioning step (not enforced here)." Card numbers / PII (if persisted) have no at-rest story (PG-6 PCI-DSS open).
5. **Scope.** Only the legal-baseline tolerance store is encrypted. `VerificationJob.ContentHash` and (the not-yet-persisted) findings/dispositions are plaintext.

**Verdict:** **config-secret only — NOT production/auditor-grade.** Cryptographic primitive is sound (AES-256-CBC, random IV); key *management* is a dev-grade config secret with no KMS, no rotation, no key versioning, no envelope encryption. This is the `business-gated` PG-4 gap and is real.

## 3. Persistence-vs-InMemory Wired-Path Reality

The Worker (`AddVeriqan`, `VeriqanOrchestrationExtensions.cs:51`) chooses persistence **conditionally on `ConnectionStrings:VeriqanDb`** (`:73-85`). **The shipped Worker has NO appsettings.json** (RC0b §Worker; `git ls-files` confirms only `Program.cs`+`.csproj`), so at runtime the connection string is absent → the `else` branch `AddVeriqanInMemoryPersistence()` (`:84,115`) registers InMemory job + disposition repos. **So the as-shipped Worker is 100% in-memory: jobs, dispositions, resume-state, and reprocess-audit all evaporate on restart.**

Even **with** a SQL connection string the persistence story is only *partial*:
- **EF-backed:** `VerificationJob` (`EfVerificationJobRepository`), `Disposition` (`EfDispositionRepository`), and the encrypted `LegalBaselineTolerances` store. Migrations exist for these.
- **InMemory regardless of SQL — no EF impl exists at all:** `IVerificationResultStore` (resume) and `IReprocessAuditRepository` are registered via **unconditional `TryAddSingleton` to the InMemory types** at `VeriqanOrchestrationExtensions.cs:99-100`, *outside* the SQL branch. There is no `EfVerificationResultStore` or `EfReprocessAuditRepository` anywhere in the tree. **Resume-across-restart (FR-22's headline) and the reprocess audit trail are non-durable by construction, in every configuration.**
- **Dead schema even on SQL:** the wired `VerificationPipeline` never writes Findings/JobVerdict/Disposition rows (§1 last two rows) — those tables exist but no code path populates them in the composed system.

Net: the durable surface is `VerificationJob` + the encrypted tolerance baseline. Everything an auditor would want to retrieve (verdict, findings, disposition history, reprocess audit, resume checkpoints) is either non-durable or never written.

## 4. Biggest Readiness Gaps (≤5)

1. **No ingestion entry point in the Worker (FR-1/PG-2).** The complete pipeline is DI-wired but unreachable — no HTTP/folder/queue intake; `IBatchProcessor` never invoked. Nothing can submit a statement to the running process. *Blocks-production.*
2. **Resume-state and reprocess-audit are InMemory-only with NO EF implementation (FR-22).** Registered unconditionally even when SQL is present; lost on every restart. The exact "resume an interrupted batch" and "immutable reprocess audit" requirements are structurally unmet. *Blocks-production.*
3. **Verdict + findings + dispositions are never persisted in the wired pipeline.** Tables/configs/migrations exist but no composed code path writes them; `DispositionService`/`AddVeriqanDisposition` is orphaned (never called by `AddVeriqan`). The system cannot produce a stored, queryable audit record of any verification. *Blocks-production.*
4. **Key management is a config-secret, not KMS/HSM (PG-4).** No managed key store, no rotation, no key-versioning, no envelope encryption; DB-level TDE explicitly deferred to ops. Below bank/auditor bar. *Blocks-production for a regulated processor (business-gated).*
5. **Worker has no config (PG-11) → defaults to fully in-memory + every bind BLOCKED.** No appsettings.json: no `VeriqanDb` CS (→ in-memory), no CSV `RootDirectory` (→ `CsvReferenceDataAdapter` can't find any institution dir → all bundles fail → BLOCKED). The shipped Worker cannot persist or reference-bind anything. Plus 2 RED persistence integration tests (seeder 14→19 drift). *Degrades→Blocks.*
