## 0. Non-goals (scope honesty — read before believing any "proves the pipeline" claim)

This epic builds a **reproducible, manifest-backed synthetic corpus** to MEASURE the extraction/verdict
pipeline against known truth. It explicitly does **NOT**:

- **Prove the real Banamex production layout.** S6.2.1 clones the **Dummie-VEC** hand-built layout
  (540×780, right-column) — a shape that does not occur in production. The real `good.pdf` (612×792,
  left-column fallback path) is a *different* layout S6.2.1 does not exercise. That layout is the
  **S6.2.2** target (owner ruling).
- **Solve the real-corpus missing-Tasa problem.** The real statements' Tasa/CAT are absent from the
  text layer for uncontrolled reasons (print-shop footer artifact) — recoverable only by OCR/raster or
  a real-layout synthetic, NOT by this Dummie-VEC clone.
- **Assert full CONDUSEF structural/typography compliance** on the synthetic PDF (§5.7): structural
  passes (Sections, FontRuns, TypographySamples, perceptual hashes) are out of scope; the manifest tags
  their expected state as `knownFixtureDefects` rather than asserting them.
- **Introduce any behavior change to `PdfPigStatementFieldExtractor`.** The generator targets the
  *existing, unmodified* extractor. If a field needs an extractor change to resolve, that is out of
  scope and a signal to re-plan, not to patch the extractor for a synthetic fixture.

**What S6.2.1 genuinely adds** (its non-redundant deliverable, since the Dummie-VEC fields are already
green today via a hand-built PowerPoint PDF): (a) the **god's-eye JSON manifest** as gold — replacing
~20 hand-copied inline expected values in the current tests; (b) a **reproducible code generator** —
retiring PowerPoint slides as test fixtures; (c) a **regression canary** that names the exact field if
the extractor's positional logic silently regresses; (d) the **substrate** (generator + manifest +
loader) that S6.2.2 (real-Banamex layout), S6.2.3 (defect injection + verdict-level), and S6.2.4+
(movements, variance, batch) all build on.

## 3. Fork 1 — Generator tech (detailed)

### Candidates considered

| Option | Absolute-coordinate control | Token-fragmentation risk | Repo fit | Verdict |
|---|---|---|---|---|
| **PyMuPDF (`fitz`) programmatic** | Exact, in PDF points, via `page.insert_text(Point, text, fontsize, fontname)` | **Lowest** — one `insert_text` call emits one content-stream text-showing run; PdfPig tokenizes on whitespace *within* a run but never fragments a run's own glyphs the way font-substitution/kerning artifacts do in `good.pdf` | Already the stack (`anonymize.py`, `enhance.py` both `import fitz`); reuses `luhn_ok`/`clabe_ok`/`rfc_checkdigit_ok`/`_make_pan`/`_make_clabe`/`_make_rfc_personal` verbatim | **Recommended** |
| HTML→PDF (WeasyPrint/Playwright) | Achievable with `position:absolute; top/left` in `pt` on a fixed `@page` box, but mediated through a layout/text-shaping engine we don't control call-by-call | Medium — a single HTML text node *usually* becomes one run, but ligatures, `%`/currency glyph substitution, or accidental nested `<span>`s can silently split a run; failures are invisible until PdfPig round-trip fails, with no obvious cause | New dependency (WeasyPrint = Python; Playwright = Node+Chromium download) not otherwise used in this repo | Rejected for S6.2.1 — reconsider only if PyMuPDF proves inadequate for something HTML/CSS is genuinely better at (e.g. justified multi-column body text on later pages, which are NOT verdict-gating) |
| reportlab | Exact, same class of control as PyMuPDF | Low, same reasoning as PyMuPDF | Not currently used anywhere in the repo — pure incremental dependency with no offsetting reuse | Rejected — no advantage over PyMuPDF once PyMuPDF is already required for defect-injection reuse |
| PdfPig `PdfDocumentBuilder` (C#) | Exact, and in the **exact same coordinate space PdfPig itself reads** (`page.AddText(text, size, PdfPoint, font)`, bottom-left origin) — zero coordinate-flip risk at all | Lowest possible (same library on both ends) | Already used for *minimal* synthetic PDFs in this test project today (`PdfPigStatementFieldExtractorTests.cs:502-505`), but only single-line smoke fixtures, not full 8-page statements with images/tables | **Not chosen for the generator**, but flagged below as the right tool for something else |

**Note on the PdfPig-Writer option:** it eliminates the coordinate-flip step in §4 entirely (write in
PdfPig points, read back in PdfPig points). It is **not** recommended as the generator itself because
(a) it's C#, breaking from the existing Python corpus-tooling stack the owner already has scripts and
workflows around, and (b) it lacks PyMuPDF's raster/image/redaction primitives needed for defect
injection (`build_scanned_doc`) and cover-box PII handling reused elsewhere. But it **is** recommended
as an optional **golden self-check probe**: a tiny xUnit `[Fact]` that writes 2-3 known tokens with
`PdfDocumentBuilder` at a target `PdfPoint`, reads them back with the real extractor's PdfPig call
path, and asserts the round-trip `Bottom`/`Left` match to within `YBandTolerance` — a fast, dependency-free
regression guard on the *conversion formula* in §4, independent of the Python generator. Optional,
not required for S6.2.1.

### Why not the handoff's tentative "HTML/WeasyPrint RECOMMENDED"

The handoff doc flagged HTML→PDF as recommended *before* this session's PdfPig/PyMuPDF recon existed.
That recon shows the actual failure mode E2.3 died to (`good.pdf`'s rate rendered as `"29"` + `".72%"`
in two separate runs) is a **token-fragmentation** problem, and the tool that gives the tightest,
most auditable control over "is this one run or two" is the one that lets you call `insert_text` once
per intended token and inspect the resulting content stream directly — that's PyMuPDF (or PdfPig
Writer), not a browser rendering pipeline. Given the existing Python stack already leans on PyMuPDF
and its FAKE-value generators are directly reusable, the crisp recommendation is PyMuPDF.

## 4. Coordinate system — the conversion formula (make-or-break detail)

PdfPig (read side, in the extractor) uses **PDF native space**: origin bottom-left, Y grows upward.
`ExtractedField.Locator.Bottom` and all the geometry-map Y-constants are in this space.

PyMuPDF (write side, in the generator) uses **page space**: origin top-left, Y grows downward — this
is what `page.get_text("words")` returns and what `page.insert_text(point, ...)` consumes as its
placement `Point`. **These are inverted relative to each other along Y.**

Verified empirically this session (not assumed): dumping
`01+Dummie+VEC+jul_ago+20252.pdf` page 1 word boxes and computing `Bottom = PageHeight − fitz_y1`
reproduces the extractor's own calibration comments to within 1-4pt (residual = descender height on
words containing descender letters — negligible against `YBandTolerance = 5.0`). Example:
fitz raw box for `"TASA"` = `(140.8, 481.8, 159.7, 491.7)`; `780 − 491.7 = 288.3`, matching the
extractor's "TASA label ≈285-290, Bottom<350" comment exactly.

**Generator rule:**

```
fitz_insert_point.y = PAGE_HEIGHT_PT − target_pdfpig_Bottom
fitz_insert_point.x = target_pdfpig_Left          # X is not inverted; same axis both ways
PAGE_HEIGHT_PT = 780.0   (page size 540 × 780, per §1)
```

`page.insert_text(fitz.Point(x, y), text, fontname="Helv", fontsize=8.0, color=(0,0,0))` places the
text **baseline** at `y` — for the all-caps/digit/percent tokens this epic cares about (no descenders
in "TASA", "CAT", "RESUMEN", amounts, percents), baseline ≈ glyph-bbox-bottom, so the formula is
direct with no fudge factor needed. For any label containing a descender letter (Spanish "g", "j", "p",
"q", "y" — e.g. "generar", "pago"), expect the *measured* `Bottom` to land 1-3pt below the target; this
is within tolerance and does not need correction, but the generator's self-check (below) should log it
so a reviewer can see it's accounted for, not accidentally masked.

**Dev-loop self-check (fast, not gold):** after writing a page, re-open it with PyMuPDF's own
`get_text("words")`, apply the same `Bottom = PageHeight − y1` flip, and diff against the target table
in §5. This catches gross placement bugs in seconds without needing .NET. **It is never the acceptance
gate** — per the standing project lesson ("calibrate from PdfPig coords, never pdftotext/PyMuPDF"),
the only authoritative gate is the C# golden round-trip test in §9, which drives the real
`PdfPigStatementFieldExtractor` via PdfPig.

| Element | Tokens | Bottom |
|---|---|---|

**Critical rule (why this isn't "any Bottom<350 percent"):** the extractor anchors on the **label**
token(s) first (`"TASA"` and/or `"CAT"`, Bottom<350 — matched **case-INSENSITIVELY** via
`string.Equals(..., OrdinalIgnoreCase)` in `ExtractTasaAndCat`, so case doesn't matter, but the
generator will emit uppercase anyway to match the fixture), then scans a **value band 0-60pt
below the label row** for percent tokens — it does not blindly scan the whole sub-350 region. The
fixture's own footer (mag-stripe/print-shop legend at Bottom≈65 and Bottom≈6.4) contains decoy
`"6.65%"` / `".29%"` tokens that are technically Bottom<350 but **60+ points below** the label row, so
they are outside the scan window and are correctly ignored. **Generator rule:** place the TASA/CAT
value row within **20-40pt below** the label row (260.0 is 23.5-28.3pt below 288.3/283.5 — comfortably
inside the 60pt window with margin), and never place any other `NN.NN%` token within that same 60pt
band elsewhere on page 1.

**Token-fragmentation rule (the actual E2.3 killer, restated precisely):** each percent value MUST be
written as **one `insert_text` call producing one token**, e.g. `page.insert_text(pt, "27.36%", ...)`.
Do **not** write the digits and the `%` sign as separate calls, and do not let two adjacent percent
values' `insert_text` calls abut with zero gap (PdfPig's word-boundary heuristic could then merge or
mis-split them). The real `good.pdf` defect was exactly this: `"29"` and `".72%"` as two separate runs
from a font-substitution artifact. One clean call per token structurally cannot reproduce that failure.

## 6. Fork 3 — Manifest schema + C# loader

### 6.1 Naming collision to avoid

`ExtractedField<T>.Provenance` (type `ExtractionProvenance`) already exists in the domain and means
**which resolution stage produced this value** (Positional / Fuzzy / Semantic / LLM — the E1-E5
fallback-chain vocabulary). The manifest's "provenance" concept from the handoff doc means something
different: **where the source document came from** (synthetic / demo-fixture-Banamex / real-CONDUSEF).
**Do not reuse the field name `provenance` for this** — the manifest schema below calls it
`sourceProvenance` to keep the two concepts from colliding in code or in review.

### 6.2 JSON schema (one file per generated PDF, same basename + `.manifest.json`)

```json
{
```

Design notes:
- `fields` is a flat map keyed by the **exact C# property name** on `PeriodSummary`/`StatementModel`
  (e.g. `"Tasa"` → `PeriodSummary.Tasa`). This keeps the manifest ↔ property mapping mechanical and
  greppable — no separate name-translation table to maintain or drift.
- `expectedStatus` is a string matching `ExtractionStatus` (`"Extracted"`, `"ExtractedInvalidFormat"`,
  `"NotExtracted"`) — including **legitimate abstentions** (per the epic's requirement), so a manifest
  can assert "this field is correctly NotExtracted" as a first-class expected outcome, not just
  "this field has value X."
- `clrType` disambiguates `decimal`/`string`/`DateOnly`/`int` for the loader's generic dispatch —
  needed because `fields` is untyped JSON but `ExtractedField<T>` is generic per-property.
- `defect` is `null` for a clean baseline, or one of `"math" | "font" | "scanned" | "abstain"` (§8) —
  carried through so a test can select "give me the bad-math variant" without parsing the filename.
- `arithmeticChecks` and `knownFixtureDefects` deliberately mirror `Fixtures/PRP2/corpus-manifest.json`'s
  existing idiom (`allowedFails`/`knownFixtureDefects` arrays with `checkId` + `reason`) — same shape,
  reviewers already know how to read it.

```csharp
namespace ExxerCube.Prisma.Veriqan.Testing.Golden;

public sealed record SyntheticFieldExpectation(
    string ClrType,
    string ExpectedStatus,

    // NOTE: ArithmeticChecks intentionally NOT on the S6.2.1 record (extraction-only ruling).

        string manifestPath,

}

// Explicit accessor map — no reflection. One line per field, added as fields are covered.
// Keeps the mapping auditable in code review instead of magic-string-matched at runtime.
public static class StatementModelFieldAccessors
{
```

## 8. Fork 5 — Defect injection

Reuse `scripts/veriqan-corpus/anonymize.py`'s injection functions **as-is** — they already operate on
a generic `fitz.Document`, not on anything Banamex-specific:

| Knob | Reused from | Effect | Manifest change |
|---|---|---|---|
| `math` | `_inject_math()` (finds a `$NNN.NN` token in a bounded region, adds a fixed +$11.00) | Breaks CL-21 arithmetic identity by exactly $11 (well above the $0.50 tolerance) | `defect: "math"`; `arithmeticChecks[CL-21].expectedOutcome = "Fail"`; the perturbed field's manifest `value` reflects the injected (wrong) amount so the test can assert the extractor still reads it correctly — only the *verdict*, not the *extraction*, should differ |
| `font` | `_inject_font()` (re-renders a heading in Courier) | CL-35 font-consistency fails | `defect: "font"`; unrelated fields unchanged |
| `scanned` | `build_scanned_doc()` (rasterizes every page, drops the text layer) | Every positional field → `NotExtracted`; text-density guard → `Blocked` | `defect: "scanned"`; every entry in `fields` gets `expectedStatus: "NotExtracted"` |
| **`abstain` (new, synthetic-only)** | New — no equivalent in `anonymize.py` because you can't ask a *real* statement to omit a real value on purpose | Generator skips writing one target field's label+value entirely (e.g. omit the TASA/CAT block) while leaving everything else intact | `defect: "abstain"`; the omitted field's manifest entry sets `expectedStatus: "NotExtracted"` with a `reason` explaining which field was deliberately dropped and why (tests the extractor's honesty path — "field genuinely absent" — independent from "field present but garbled") |

`abstain` matters because it is the **only** way to construct a *clean, ground-truth-known* "genuinely
absent field" test case. Every existing abstention in the real corpus (`good.pdf`'s missing TASA) is
absent for an *uncontrolled* reason (print-shop artifact) with no manifest to confirm the extractor's
`NotExtracted` is *correct* rather than a false negative on a value that secretly is there. Synthetic
`abstain` closes that gap — it is the god's-eye proof that "abstain" and "extract" are both being
tested against known truth, not just "extract."

Injection order: generate the clean baseline (all fields present, geometry per §5) → apply `math`/`font`/
`scanned`/`abstain` as **separate output variants from the same seed**, mirroring `anonymize.py`'s
`run_batch()` pattern (`good.pdf` + N defect variants from one SUT master) — not as combinatorial
cross-products in S6.2.1 (that's variance, §2 fork 6, deferred).

## 11. Residual risks

1. **PyMuPDF's `insert_text` font substitution.** Requesting `fontname="Helv"` uses PyMuPDF's base-14
   alias (no embedding needed), which should be safe and predictable — but this must be verified by
   actually running the §9 golden test, not assumed from documentation. If PyMuPDF ever substitutes a
   metrically-different font, token X-widths would shift, which is irrelevant to X *start* positions
   (which is all the extractor keys on) but could matter if two adjaccent tokens are placed close
   enough to abut — mitigated by generous token spacing per §5's measured gaps.
2. **`abstain` semantics collide with the epic's own "abstain, never fabricate" cardinal rule if
   built carelessly.** The `abstain` defect knob (§8) must be clearly manifest-tagged as an
   *intentional test fixture defect*, never confused with a *real* extraction abstention policy
   change. Keep it entirely inside `synth_gen.py`/the manifest; it must never leak into
   `PdfPigStatementFieldExtractor` itself.
3. **Page count/structural fields (§5.7) will show as non-compliant** on the S6.2.1 PDF (same as the
   existing Dummie-VEC fixtures already do, per `corpus-manifest.json`'s own `knownFixtureDefects`)
   — this is expected and must be manifest-tagged, not silently left to fail unexplained in a future
   CI run that widens what gets asserted against this fixture.
4. **PyMuPDF version drift.** `anonymize.py`/`enhance.py` don't currently pin a PyMuPDF version in a
   lockfile visible in this recon; the generator should pin one explicitly (or add a
   `requirements.txt`/`pyproject.toml` to `scripts/veriqan-corpus/` if one doesn't already exist) so
   the geometry table in §5 doesn't silently drift if `insert_text`'s baseline behavior ever changes
   between PyMuPDF releases.
